# Journal-Eintrag: 02.12.2025 - Session 6

## Session 6: Lineup Builder Bug Fixes & UX Improvements (Spätabend, 2. Dezember)

### Problem
User berichtet 4 kritische Bugs im Lineup Builder:
1. ❌ **Bank Overflow**: Bank kann >4 Spieler haben trotz Validierung
2. ❌ **Name Overflow**: Guimaraes Name "verglitcht"
3. ❌ **Auto-Positioning**: Spieler gehen links statt zur gewählten Position
4. ❌ **Fehlende UX-Buttons**: Keine klaren "Zur Bank" / "Zur Startelf" Buttons

### Analyse

#### Bug #1: Bank Overflow (Race Condition)
**Ursache**: `benchSize >= 4` Check BEVOR State-Update
```typescript
// FALSCH:
const benchSize = squad.length - xiIds.length
if (benchSize >= 4) { ... } // Zu spät!
setSquad(prev => [...prev, player]) // State ändert sich NACH dem Check
```

**Problem**: Zwischen Check und State-Update kann ein anderer Event passieren.

#### Bug #2: Name Overflow
**Ursache**: `line-clamp-2` funktioniert NICHT mit `flex items-center justify-center`
```tsx
// FALSCH:
<div className="line-clamp-2 flex items-center justify-center">
  {player.name}
</div>
```

CSS `line-clamp` benötigt `display: block` oder `display: -webkit-box`, KEIN Flexbox!

#### Bug #3: Auto-Positioning
**Analyse**: 
- `xiIds` ist nur `number[]` - keine horizontale Position-Info
- `setXiIds(prev => [...prev, newIndex])` hängt ans Ende → immer rechts
- `groupPlayersByFormation()` behält Array-Reihenfolge bei
- **Lösung komplex**: Slot-System mit Insert-Index nötig
- **Entscheidung**: SKIP für jetzt - UX-Buttons wichtiger

### Entscheidungen

**1. Future-State Validation**
- **Warum**: Race Conditions vermeiden
- **Alternativen**: 
  - Immutable State Libraries (Immer.js) → Overkill
  - State-Locks → Zu komplex
- **Gewählt**: Einfache `futureBenchSize = current + 1` Berechnung

**2. Line-Clamp Fix**
- **Warum**: `line-clamp` + `flex` incompatibel
- **Alternativen**:
  - `truncate` (nur 1 Zeile) → Zu wenig Platz
  - JavaScript-basiertes Clamping → Overhead
- **Gewählt**: `line-clamp-2` + `break-words` ohne Flex

**3. Auto-Positioning Skip**
- **Warum**: Komplexität vs. Nutzen
- **Alternativen**:
  - Slot-Mapping-System → Große Refactoring
  - Position-Index-Array → Zusätzliche State-Komplexität
- **Gewählt**: SKIP - UX-Buttons reichen für MVP

**4. Button-Platzierung**
- **Warum**: Klar erkennbare Aktionen
- **Alternativen**:
  - Nur Icons → Unklar
  - Nur X-Button → Multi-funktional verwirrend
- **Gewählt**: Separate Buttons mit Icons + Text

### Warum so?

**Future-State Pattern**:
```typescript
// FALSCH (Race Condition):
if (benchSize >= 4) { ... }
setState(...)

// RICHTIG (Future-State):
const future = current + delta
if (future > limit) { ... }
setState(...)
```
→ Garantiert konsistente Validierung VOR State-Mutation

**Line-Clamp ohne Flex**:
```css
/* FALSCH */
.card { display: flex; line-clamp: 2; }

/* RICHTIG */
.card { display: block; line-clamp: 2; break-words: true; }
```
→ CSS Spec: `line-clamp` nur mit block/webkit-box, nicht mit flex

**Separate Buttons statt Multi-Function X**:
```tsx
// VORHER: X macht alles (unklar)
<button onClick={onRemove}>×</button>

// NACHHER: Klare Aktionen
<button onClick={onRemove}>× Entfernen</button>
<button onClick={toBench}>🪑 Zur Bank</button>
<button onClick={toXI}>⬆️ Zur Startelf</button>
```
→ UX-Prinzip: Explicit is better than implicit
