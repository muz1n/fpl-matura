## Reflexion (kurz)
- Gut: Hybrid-Ansatz (Season-Präfix optional) vermeidet Breaking Changes
- Schwierig: PowerShell-Syntax für Terminal-Commands (`&&` nicht erlaubt)
- Gelernt: Fallback-Logik in APIs wichtig für Rückwärtskompatibilität

## Entscheidung
- Hybrid-Ansatz: API versucht zuerst `predictions_{season}_gw{N}_{method}.json`, dann Fallback auf `predictions_gw{N}_{method}.json`
- Vorteil: Keine Breaking Changes, schrittweise Migration möglich

## Alternativen (kurz)
- Nur Season-spezifische Files → Re-Generation aller Predictions nötig
- Season nur für Historical Evaluation → weniger flexibel
- Verzeichnis-Struktur `season_{season}/` → komplexere Pfad-Logik

## Warum so?
- Balance zwischen Flexibilität und Kompatibilität
- Alte Predictions bleiben funktionsfähig
- UI zeigt nur verfügbare Seasons mit vollständiger Datenqualität

## Fehler & Learnings
- PowerShell `&&` nicht unterstützt → Semikolon oder einzelne Commands nutzen
- `# type: ignore` vermeidet Circular Import Problems
- Backend-`suggestion`-Feld sehr hilfreich für User-Guidance
